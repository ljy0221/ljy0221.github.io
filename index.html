원인을 규명하고 결과를 재측정하는 백엔드 개발자

경기대학교 컴퓨터공학부를 졸업(2025.02)하고, 삼성청년SW·AI아카데미를 수료(2025.07~2026.06)했습니다.

팀 프로젝트에서 분석·집계와 발송 결과 적재 모듈을 맡았습니다. 메시지 단건 INSERT 구조를 배치 적재로 바꾸고 원인이 된 PK 생성 전략까지 규명했습니다.

설계 과정에서 선택지와 기각 사유를 ADR로 남겼습니다. 팀 ADR 19건 중 12건을 작성했습니다.

프로젝트가 끝난 뒤에는 제가 만든 구간의 성능을 다시 측정해 성립하는 조건의 범위를 함께 정리했습니다.

Butterfly CRM에서 실제로 겪은 일입니다. 설정 파일에는 배치가 켜져 있었는데, 실행된 SQL은 한 건씩이었습니다.

설정

hibernate.jdbc.batch_size: 1000
hibernate.order_inserts: true

@Id
@GeneratedValue(strategy = IDENTITY)
private Long id;

실제 실행된 SQL (재구성)

insert into notification_logs … 1행insert into notification_logs … 1행insert into notification_logs … 1행insert into notification_logs … 1행insert into notification_logs … 1행…

메시지 1건마다 INSERT 1건, 커밋 1회

원인
PK 생성 전략이 IDENTITY라 Hibernate가 PK 값을 받으려고 INSERT를 즉시 실행하고, 배치 설정은 조용히 무효가 됩니다.
조치
JPA를 우회한 배치 적재로 바꾼 뒤 적재 처리량이 평균 91.8건/초에서 1,485.3건/초가 됐습니다. 측정 조건과 대가 보기
